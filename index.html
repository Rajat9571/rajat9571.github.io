Remote-job scraping & enrichment platform

production · AIDOOS

Matching people (or AI agents) to real job openings only works if the pool of openings stays current — but 15+ job sites each present that data differently, and each defends against being scraped differently, so this can't be done by hand and it can't be one script copy-pasted everywhere. If a scraper breaks the moment a site changes its layout, the pipeline quietly goes stale and nobody notices until the listings dry up. This keeps that pipeline alive every day: pulling fresh listings from 15+ sources, using whatever's actually the cheapest reliable approach per site rather than the same heavy tool everywhere, then cleaning and structuring every listing with an LLM before it's used for matching.

▸ how it actually works

Every one of the 10 site-specific scrapers funnels through the same shared pipeline: collect candidate URLs → dedup check → visit only the new ones → LLM enrichment → insert with retry. The dedup step happens first — each scraper POSTs its URL list to a filter-new-urls API before ever opening a detail page, so no time is wasted re-fetching pages the system already has.

The part that actually varies is how each site is approached. I looked at this closely enough to be honest about it: only 1 of the 10 sites (WeWorkRemotely) needed genuine browser-fingerprint stealth — selenium-stealth spoofing WebGL vendor/renderer, disabling automation flags, randomized human-like delays. The other 9 don't fight detection head-on at all: some hit the site's own internal JSON API directly and skip HTML entirely (no browser needed), one parses the server-rendered __NEXT_DATA__ JSON blob instead of launching Chrome, and the rest just spoof a normal browser User-Agent header. That's a deliberate lesson from this project: architecting around a problem is usually cheaper and more reliable than brute-forcing past it.

Insertion has real retry logic — a 429 rate-limit gets retried with linear backoff (5s, 10s, 15s across 3 attempts), while any other failure gives up after one try. Data enrichment runs every scraped listing through OpenAI/DeepSeek to structure it (title, tech stack, intent, summary) before it's stored, with embeddings pushed into Qdrant so listings can be matched against AI agent profiles by meaning, not just keywords.

ebol — document scanner & quality gate

production · AIDOOS

Replacing manual data entry with "just snap a photo of the document" only works if what gets snapped is actually readable — a blurry photo, an empty frame, or a photo of the wrong page all waste an expensive OCR+LLM call and produce garbage data on the other end, and the person scanning it often can't tell it went wrong until later. This app catches that on the phone itself, before the photo ever leaves the device: checking sharpness and whether there's even real text in frame, in real time, so only genuinely good scans get read and turned into structured data automatically.

▸ how it actually works

The gate runs two stages, entirely on-device, before an image is ever sent to an LLM — the goal is to catch the obviously-useless captures (blank frame, out-of-focus blur, wrong subject) without spending an API call finding out.

Stage 1 — pixel quality: measures the variance of the Laplacian (a sharpness/edge-strength signal) and edge density on the blurred grayscale image. The blur-before-measuring step was a deliberate fix for a real false positive: raw sensor noise on a blank surface scored almost as high as real text, because noise and edges both spike the raw Laplacian. Denoising first collapses the noise while real printed structure survives, giving a clean separation (blank/blurry ≈ 3–10, real document ≈ 730). Thresholds were calibrated against synthetic blank/noisy/blurry/sharp samples, not guessed.

Stage 2 — is there actually text: a sharp photo of the wrong thing still passes stage 1. A Tesseract.js OCR pass (fully in-browser, no server round-trip) checks whether it can read any confident text at all — filtering words below a 55% confidence score, requiring at least 8 confident characters to count as "readable."

Both stages fail open, not closed — if OpenCV or Tesseract can't load or the image can't be decoded, the gate returns "ok, skipped" rather than blocking a scan it couldn't actually evaluate. On the scanning side, there's also live ML document-boundary detection with focus feedback, so the camera nudges the user before a bad capture even happens.

codeverify — multi-provider verification engine

production · AIDOOS

When someone on a team says a task is "done," there's usually no easy way to check that against what was actually pushed — a lead either takes it on trust or spends their own time digging through the code, and that's true whether the lead is technical or not. This closes that gap: point it at a codebase (public repo, private repo, or a plain zip upload) and describe the tasks that were supposed to be built, and it reads the real code and returns a verdict per task — done, partial, or not done — with the actual evidence, not just a guess. That turns "trust me, it's done" into something a manager can actually verify, which is really what it's for: accountability and honesty in how progress gets reported.

▸ how it actually works

A codebase can come in three ways — a public repo URL, a private repo connected via GitHub OAuth, or a zip upload — and each one is tied to a lead_email, the person accountable for reviewing it. From there it's the same pipeline regardless of source: index → link → judge.

Indexing walks the repo (skipping node_modules, binaries, anything over 1MB, and whatever the repo's own .gitignore excludes), splits files into chunks on blank-line boundaries (soft cap 80 lines, hard cap 150), and builds a Merkle tree over SHA-256 hashes of every chunk/file/directory. That tree is the reason re-indexing is cheap: on a re-scan, a chunk only gets an (expensive) LLM summarization + embedding call if its hash doesn't already match a stored node — unchanged code costs nothing to re-index.

Linking is query-time: a task description ("users can reset their password") gets embedded and matched against stored chunk embeddings via vector search — but instead of returning just the top-K similar snippets, it expands each matched file back to all of its chunks in order, so the judge sees whole files instead of a similarity-ranked sample that might cut off the part that actually matters.

Judging is LLM-as-judge, not static analysis or test execution — the model reads the retrieved code and returns a structured verdict (done / partial / not_done, confidence, evidence). Crucially, the verdict isn't trusted at face value: a done claim under 80% confidence gets capped down to partial, and under 25% it's forced to not_done — a deliberate trust-but-verify layer on top of the raw model output.

Multi-provider BYOK routes through one shared call_llm() entry point: no key → DeepSeek (platform's own, cheapest); customer's own key → Anthropic or OpenAI or DeepSeek, each normalized to the same response shape so the rest of the code never needs to know which provider answered. Customer API keys are Fernet-encrypted at rest and validated with a real 1-token test call before being saved, so a bad key gets rejected immediately instead of failing silently mid-scan later.

▸ how the integration & invitation flow works

The OAuth flow does a bit more than log a token: on callback, it discovers the user's Asana workspaces, and if there's more than one, it deliberately leaves the choice to the frontend picker rather than guessing. Both access and refresh tokens are encrypted at rest (Fernet), and the client transparently refreshes an expiring token before any API call rather than failing and asking the user to re-auth.

Project import runs as an async job (Celery) with progress polling, because pulling every task for a project isn't instant — the frontend shows a live "N of M imported" state instead of a spinner with no feedback.

The invitation piece is the one I'd highlight most: a signed, time-limited magic link (Django's cryptographic signing, no separate login required) gets emailed to talent/delivery managers assigned to a project. Clicking it calls Asana's addUser/addMembers APIs directly, using the organization's own OAuth grant — so there's no separate "accept invite" step on Asana's side, the person just lands in the project. It's idempotent (a flag stops duplicate sends) and retries failed emails with backoff while never re-sending to people who already got theirs.
